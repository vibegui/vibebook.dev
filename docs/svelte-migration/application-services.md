# Direct application service foundation

This source checkpoint starts at `95379f8`. `createApplicationServices` constructs one PersonalSession, RoomsSession, AppNavigation/creator/search, AccountSession, AgentsService, RootRoomSession, personal-channel coordinator and PWA/logout owner. It does not mount components, register views, build HTML, copy the legacy host to TypeScript or change layout/assets. RootApp/RoomShell adoption remains the next integration step; the currently served entry is unchanged.

`createBrowserApplicationServices({ window, document, shellVersion, onIdentityReset })` binds actual browser effects and existing typed APIs, the one PWA service and the one device-lock owner. It returns `BrowserApplicationServices`, including the existing native owners, language/locale/copy, device and typed actions. `copy.ts` is the exact pure dependency from accepted dead-host retirement `6ba6fbc`; no other retirement changes are copied. Core services can instead receive typed API, clock, transport and PWA factories for meaningful non-browser ownership fixtures. Additive `runnerFetch` passes through AgentsService to its existing fixed-origin LocalRunner; production defaults and credential omission are unchanged.

The public `state` contains route/href/navigation generation, pane, version availability, known session denial and lifecycle only. `rootRoom.state` is the existing RootRoomSession readable, not another room projection/reducer. Account data/drafts remain in Personal; each feature keeps its existing API validation and mutation/confirmation rules. The development version sentinel never creates an update banner.

RootApp can construct services once, call `start()` on mount and `dispose()` on teardown. RoomShell receives services directly, reads `rootRoom.state`, obtains `roomScope()`, and installs its one specialized `ApplicationRoomAdapter` with `attachRoom(scope, adapter)`. Adapter methods handle room-feature reset, Viewer consumePop/deferNavigation, canonical transitions and target intents. This is one active room lifetime, not a production component registry. Returned cleanup detaches only that exact installation, so stale cleanup cannot remove a replacement.

Initial deep targets are buffered until the matching room/account/RootRoom generation/navigation generation exists and RoomShell attaches. Delivery is once, removes the pending record before callbacks, validates the selected thread against the canonical room and supplies an immutable intent scope. Old room callbacks, account replacement, route changes and disposal cannot redirect a newly attached shell. `actions.navigate/selectThread/selectPane`, router pop/generation, `navigation` and `account` provide direct composition seams. RootShell still owns sheet/Viewer history and visual state through the specialized adapter; services invent no fallback history timer.

`appsAuthority()` returns the same services-owned authority for the catalog and embeds of one actual Book connection. Its listener evicts immediately. RootRoomSession's `cacheAllowed` reads this exact denial before cache insertion and public state publication; the root regression includes a public subscriber that reenters navigation at that boundary. Replacing Book/account ownership disposes that authority rather than clearing a denied flag on cached membership.

Observed account revision changes synchronously clear private root/cache/agents/account/navigation state, cancel the personal channel, run one account-draft reset callback and reset the captured room adapter. A generation-fenced microtask reactivates the current URL unless newer navigation supersedes it. A known global unauthenticated response is terminal for these document owners: Personal's new `revoke()` fences pending reads and clears canonical caches/drafts, all private owners are disposed, PWA is disposed once and `sessionDenied` is published before the existing safe opt-in login redirect. `actions.sessionLost()` is for already-classified global unauthenticated failures only; membership/report errors and remote MCP `sign_in` do not belong there. No endpoint, automatic mutation retry or new consent flow is introduced. Logout retains the existing PWA cleanup warnings/single-flight/observed-account fence; it does not claim server-cookie atomicity.

Eight lifecycle fixtures are authored for start/dispose, initial late attachment, same-room route/thread/pane behavior, stale teardown/navigation, pre-publication Apps cache veto, synchronous identity reset/late callbacks, PWA logout ownership and known-401 clearing before redirect. They use real typed existing owner implementations with explicit API/transport/browser ports; they are unit fixtures, not Worker/browser evidence. Connection/tooling/format registrations are included. No install, formatter, compiler, test, build, Worker or browser has run for this checkpoint. Public assets, vanilla and the primary CLI are unchanged.
