# Protected file browser cache boundary

Private browser caches belong to the browser profile, not the signed-in account. Protected raw-file responses now vary by `Cookie`, so an account change cannot reuse a fresh representation obtained with another cookie. Existing `private, max-age=86400` freshness, bytes, HTML sandbox, escaped viewer response and byte ranges remain unchanged. Protected versioned icon/avatar responses also explicitly set `Vary: Cookie` after the edge-cache lookup, including when that edge entry predates this change. The edge cache remains shared behind the existing authorization checks; it holds the same versioned bytes, not an authorization decision.

The current raw-file route authenticates the request and checks room membership before accessing R2. It does not implement ETag, Last-Modified, conditional 304 or an edge-cache lookup. A client supplying If-None-Match still reaches authorization and the normal file path; this change introduces no new conditional-response bypass.

This narrowly fixes cookie-changing account transitions. It does not invalidate bytes already visible in a document, retroactively rewrite predeployment fresh browser-cache entries, or change the existing freshness policy for permission revocation while the same cookie remains in use. Previously cached responses without `Vary` can remain fresh until their old deadline; rollout/runtime reports must not claim retroactive cache removal.

The focused pure fixtures exercise the actual common file headers and preserve MIME, filename escaping and sandbox policies. They are not proof of browser cache behavior or R2 range integration.

The real Viewer browser gate should use one browser context and the exact same file URL, without cache-busting, request interception or a fetch cache override: account A uploads a unique file to its private room and loads it through an actual browser fetch/media element; the supported local DEV identity operation switches that context's cookie to account B, who is not a member; requesting that unchanged URL must contact the Worker and return the existing 403 access response rather than A's cached bytes. Include a return to A for successful bytes and exercise both ordinary content and an existing Range/media path. A DEV identity cookie switch proves this cache boundary, not production sign-in/session issuance. Existing bytes painted in A's page are outside this HTTP-cache gate.
